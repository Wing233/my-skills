# 质量检查表（quality-checklist）

裁决前对每个候选必查。死仓库的高星项目照样否决。

## 星数判断（主排序，不设死线）

- 主流领域（web 框架、常用工具）：1000+ 星是强信号
- 细分领域：几百星可能就是该领域最好的
- 星数是**排序依据**，不是**准入依据**——准入看下面三硬信号

## 三硬信号（任一不过就否决/降级）

1. **最近提交 ≤ 12 个月**（`gh repo view` 看 "last commit"；网页看 commit 历史）
2. **非 archived**（仓库页有 Archived 标记 = 死了）
3. **有 LICENSE**（没 license 的代码默认"保留所有权利"，fork 有法律风险）

## 许可证速查（fork/改造发布时）

| 许可证 | 含义 |
|---|---|
| MIT / Apache-2.0 / BSD | 宽松，随便用、改、发布（保留版权声明） |
| GPL / AGPL | 传染性：你改后发布的代码也要开源同协议 |
| 无 LICENSE | 默认版权保留，不能合法 fork 发布 |

## fork 三问（裁决选 fork 前，逐条走）

1. **扩展点优先**：上游有没有插件机制/hooks？能不改上游代码就达成吗？
2. **PR 优先**：改动通用吗？能提交回上游让大家都受益吗？（这样你零维护债）
3. **硬 fork 最后**：上面都不行才 fork。fork 后必须提醒用户这些债：
   - 上游更新要手动跟（merge conflicts 会越来越多）
   - 安全补丁要自己移植
   - 除非必要，尽量保持 diff 最小，别大改结构

## 其他降分项

- issue 大量积压无回应 → 维护者已离开
- 文档稀烂 / 无测试 → fork 成本高
- 代码量远超需求 → 组装时会带进大量不需要的东西
