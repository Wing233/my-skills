# 防重复造轮子（avoid-reinvention）

你在动手实现任何东西之前，先花几分钟查"这件事是否已经有人做好"。大部分想法都
能找到现成的开源方案：直接拿来用、组装改造，往往比从零写更快、更稳、更少维护债。

## 两个触发时机（保持粘性）

1. **开工前**：用户提出一个新想法/新工具/新功能时，先跑本流程再动手。
2. **开发中途**：本流程保持激活——每当遇到新的子功能边界（新模块、新交互、
   新依赖），在动手写之前，用该子功能的"能力描述"重跑一次阶梯（阶梯是
   递归可用的，一个 20 行的检查就够）。
   例：正在做 A，突然需要"拖拽排序"，就把「拖拽排序」当新点子，从 L2 开始查。

## 复用阶梯（按顺序查，任何一层命中就进入裁决）

| 层 | 查什么 | 目的 |
|---|---|---|
| **L0** | 澄清能力需求：把点子翻译成"我需要它能 X / Y / Z" | 按能力搜，命中率远高于按成品名搜 |
| **L1** | 自己项目内：现有依赖、代码库里已有模块 | 最容易漏的一层，先查自己 |
| **L2** | 包注册表：npm / PyPI / crates.io | 找积木（库），组装只需写胶水 |
| **L3** | GitHub 开源项目：整体方案、可 fork 对象 | 找成品或半成品 |
| **L4** | awesome-lists：`awesome-<领域>` | 该领域生态地图，一眼看全 |
| **L5** | 现成托管工具/SaaS/CLI | 一行代码都不用写，直接白嫖 |

具体搜法见 `references/search-playbook.md`（读它再动手搜）。
质量硬信号与 fork 护栏见 `references/quality-checklist.md`（裁决前必读）。

## 裁决：五选一

1. **直接用现成工具**（L5 命中）——什么都不写。
2. **组装积木只写胶水**（L2 命中）——依赖现有库，只写组合逻辑。
3. **fork 改造**（L3 命中且通过 fork 三问）——以开源项目为基础改造。
4. **当参考不抄**——看别人的架构/实现，自己写。
5. **自研最小版**——确实没有合适的，写最小可用版本。

## fork 三问（裁决选 3 之前必须走完）

1. 能否用**插件/扩展点**达成，不改上游？
2. 能否给上游**提 PR**，改完大家一起用？
3. 都不行才**硬 fork**——并提醒：fork 要还债（跟上游更新、合并冲突、安全补丁移植）。

## 例外

用户明确说**练手/学习**（"我想学怎么写 X"）时：只报告，不阻拦动手。

## 输出格式

固定使用 `references/report-template.md` 的模板，产出报告后把裁决明确写出来，
不要只扔一堆链接让用户自己判断。
